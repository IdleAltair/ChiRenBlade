## 1. 免耗 BaseValue-only：三判据

样本：50 条 `shachi settle(base)`，每条 +150/600/1200ms 读回。

### 超上限待结算 —— 本轮未触发，但非结构性消除
- 所有 base 写入值 ≤ 760.0，无一超 Shachi_Max。
- 关键前提：**每条写入时 base == cur**（如 `base 567.61->694.2 cur 567.6`、`base 717.44->760.0 cur 717.4`）。因此 `add = min(refund, max(0, max - current))` 在 base==cur 时等价于把 base 也钳在 max 内。
- REVIEW 担心的"base 已高于 current 时连续退款堆超上限"需要**写入时 base > cur（存在待结算缺口）**这个前提。本轮 50 条写入全部 base==cur，前提没出现，所以风险没被采到，**不等于被证明安全**。
- 待结算缺口确实存在，但出现在读回阶段而非写入阶段：readback `cur=129.74 base=172.30 (wrote 172.3)`、`cur=590.88 base=633.44 (wrote 633.4)`、`cur=575.54 base=618.10 (wrote 618.1)`，缺口恰好 = 一笔 consumed（42.56）。即退款留在 base，cur 滞后，等结算事件（停手/普攻）追平。

### base 持久 —— 证实（无原生消耗时）
- 无后续消耗时 base 恒等于写入值：readback 3022/3173/3223/3240 `base == wrote`。
- 连招中 base 掉回是**原生消耗后续重击**，不是退款丢失：`wrote 698.0 → +1200ms base 558.93`（−139）、`wrote 563.7 → 216.70`（−347）。每激活仍各退各的，consumed 归因正确（126.6/84.6/42.6，付费半退 21.3/42.3）。
- 自然回气可合法抬高 base：`wrote 676.9 → 704.35`（+27.5）、`wrote 75.0 → 272.41`（+197，回气+结算）。

### 漏退 / 多退 —— 未见
- 每激活一条 settle，refund = consumed×(1−keepScale)，封顶 max−current；无 raw 差值过退。
- 低杀气也退：`base 32.4->75.0 cur 32.4`（consumed 42.6）。天赋"杀气不足仍可释放连招"已排除拒绝发动边界（仍待低杀气启动/取消/其他重击类型单测）。

### 缺口（下轮补）
1. **settle 日志没有 max 字段**。REVIEW 要求"每次写前 base/cur/max"，目前只有 base/cur。需在 `ScheduleShachiSettlement` 的 LogKey 补 `max %.1f`（maxValue 已在函数内读到，只是没打印）。

- **bAutoManageAttachment=false / AutoAttachParent=nil / AutoAttachSocketName=None / bAutoDestroy=false**：原生池组件**不用自动附着配置**。active=true 时运行时 GetAttachParent=CharacterMesh0、GetAttachSocketName=pelvis；active=false 时脱附。即 attach/detach 是**运行时手动调用**，不是组件配置驱动。

### 对复刻链的含义
- 自建普通 NiagaraComponent，**不依赖 auto-attach/auto-manage**（与原生一致：autoManage=false、autoDestroy=false）。
- 手动 `K2_AttachToComponent(CharacterMesh0, "pelvis", ...)` 附着、手动 detach 熄灭。
- 仍受 REVIEW 的 crash 约束：三份 dump 崩在 `UE4SS.dll+0x2DB4D1`（`mov rcx,[rax+0x70]`, RAX=0），是 UE4SS 内部参数转换/生命周期空指针，**pelvis 不是崩溃解**。配置正确不代表调用签名正确。下一步必须先验 AddComponentByClass / K2_AttachToComponent / SetAsset 的真实 UFunction 签名（schema.txt 是属性/枚举映射，不是签名清单），再走空组件→毒→火隔离。
